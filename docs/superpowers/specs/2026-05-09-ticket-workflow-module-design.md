# Ticket Workflow Module Design

**Date:** 2026-05-09
**Project:** Bicol University Service Request System (BUSRS)
**Scope:** End-to-end ticket workflow — student submission portal + admin processing panel (core flow + chat, no real-time WebSockets)

---

## Stack

- Laravel 13, PHP 8.4
- Livewire 4 + Flux UI 2 (student portal)
- Filament v5 (admin panel)
- `spatie/laravel-permission` for role guards
- `wire:poll` for chat refresh (no Reverb in this phase)

---

## Architecture

Two routing domains sharing one data layer.

- `/portal/*` — Livewire full-page components for students (role: `student`)
- `/admin/*` — Filament v5 panel for staff (roles: `staff`, `office_admin`, `super_admin`)

Both sides read/write the same tables: `tickets`, `ticket_history`, `ticket_messages`, `ticket_attachments`, `forwarding_logs`.

---

## Section 1: Student Portal (`/portal/*`)

### Routes

```
GET  /portal/tickets              → My Tickets list
GET  /portal/tickets/create       → Multi-step submission form
GET  /portal/tickets/{ulid}       → Ticket detail (timeline + chat)
```

All routes protected by `auth` + `verified` middleware with a `role:student` guard.

### 1.1 My Tickets List

**Component:** `App\Livewire\Portal\TicketList`
**View:** `resources/views/livewire/portal/ticket-list.blade.php`

Displays the authenticated user's tickets ordered by `created_at` descending. Each row shows:
- ULID reference (e.g. `TKT-01JV…`)
- Subject
- Office name
- Status badge (color-coded by `TicketStatus` enum)
- Priority badge
- `updated_at` timestamp

No pagination required in this phase — soft-limit to 50 most recent.

### 1.2 Multi-Step Ticket Submission

**Component:** `App\Livewire\Portal\CreateTicket`
**View:** `resources/views/livewire/portal/create-ticket.blade.php`

Five sequential steps managed by a `$step` integer property (1–5). Moving forward validates the current step; moving back is always allowed. Validation per step:
- Step 1: `office_id` must be selected (required)
- Step 2: `service_category_id` must be selected (required)
- Step 3: `service_type_id` must be selected (required)
- Step 4: all `service_type_fields` where `is_required = true` must be non-empty; file fields validate mime type and size
- Step 5: no validation (read-only review)

| Step | Description | Data loaded |
|------|-------------|-------------|
| 1 | Select Office | `offices` where `is_active = true`, ordered by `sort_order` |
| 2 | Select Category | `service_categories` filtered by chosen `office_id`, `is_active = true`, ordered by `sort_order` |
| 3 | Select Service | `service_types` filtered by chosen `service_category_id`, `is_active = true`, ordered by `sort_order`. Shows `sla_days` and description. |
| 4 | Fill Details | Dynamic fields from `service_type_fields` for the chosen `service_type_id`, ordered by `sort_order`. Renders each field by `field_type` (text, textarea, select, checkbox, file, date). File inputs route through a temporary upload handler. Answers stored in `$customFields` array keyed by `service_type_fields.id`. |
| 5 | Review & Submit | Read-only summary of all answers. Submit button creates the ticket. |

**On submit:**
1. Create `Ticket` record: `requester_id = auth()->id()`, `status = Pending`, `priority = Normal`, `office_id`, `service_type_id`, `custom_fields` (JSON). ULID auto-generated by model boot.
2. Insert `TicketHistory` row: `event_type = Created`, `actor_id = auth()->id()`.
3. Redirect to `/portal/tickets/{ulid}`.

**Validation rules (Step 4):**
- Required fields (`is_required = true`) must be non-empty.
- `file` fields: max 10 MB, allowed mime types: `pdf`, `jpg`, `jpeg`, `png`.

### 1.3 Ticket Detail

**Component:** `App\Livewire\Portal\TicketDetail`
**View:** `resources/views/livewire/portal/ticket-detail.blade.php`

Two-panel layout:

**Left — Status Timeline**
Reads all `TicketHistory` rows for the ticket ordered by `created_at` ascending. Renders each as a timeline node:
- Completed steps: filled circle with checkmark
- Current step: highlighted circle
- Future steps: empty dimmed circle

Timeline steps shown (in order): Submitted → Assigned → In Progress → Resolved/Closed

**Right — Chat Thread**
Reads `TicketMessage` rows where `is_internal_note = false`, ordered by `created_at` ascending. Refreshes via `wire:poll.5s`.

Student can send a message (creates a `TicketMessage` with `sender_id = auth()->id()`, `is_internal_note = false`, `is_canned_response = false`).

File attachments on messages: student can attach one file per message. Creates a `TicketAttachment` row linked to the message.

Seen status: `seen_at` on a message means the *other party* has read it.
- When student opens ticket detail → batch-update `seen_at = now()` for all messages sent by staff where `seen_at = null`. Staff can then see "✓✓ Seen" on their messages.
- When staff opens ticket detail → batch-update `seen_at = now()` for all messages sent by the requester where `seen_at = null`. Student can then see "✓✓ Seen" on their messages.

## Section 2: Admin Panel (`/admin/*`)

Filament v5 panel. Access restricted to roles: `staff`, `office_admin`, `super_admin`.

### 2.1 Ticket Resource

**Resource:** `App\Filament\Resources\TicketResource`

**Scope (global scope):**
- `staff` → tickets where `office_id` in their assigned offices
- `office_admin` → tickets where `office_id` in their assigned offices
- `super_admin` → all tickets

**List columns:**
- ULID reference (monospace, copyable)
- Subject
- Requester name
- Office name
- Status badge (enum label + color)
- Priority badge
- Assigned staff name (or "—")
- `updated_at`

**Filters:** Status (multi-select), Priority (multi-select), Assignee (select from office staff), Date range.

**Default sort:** `updated_at` descending.

### 2.2 Ticket Actions

All actions log a corresponding `TicketHistory` row with `actor_id = auth()->id()`.

#### Assign to Staff
- **Type:** Filament `Action` (modal)
- **Form:** `Select` listing active staff in the ticket's office (`office_user` pivot)
- **On save:** Set `tickets.assigned_to`, update `status` to `Assigned` if currently `Pending`. Insert `TicketHistory` row (`event_type = Assigned`, `from_status`, `to_status`).

#### Change Status
- **Type:** Filament `Action` (modal)
- **Form:** `Select` with allowed transitions from current status. Optional note field.
- **Allowed transitions:**

| From | To options |
|------|-----------|
| Pending | Assigned, Cancelled |
| Assigned | InProgress, OnHold, Cancelled |
| InProgress | OnHold, Resolved, Cancelled |
| OnHold | InProgress, Cancelled |
| Forwarded | InProgress (after acceptance) |
| Resolved | Closed |

- **On save:** Update `tickets.status`. If transitioning to `Resolved`, set `resolved_at = now()`. If `Closed`, set `closed_at = now()`. Insert `TicketHistory` row (`event_type = StatusChanged`, `from_status`, `to_status`, `note`).

#### Forward to Office
- **Type:** Filament `Action` (modal)
- **Form:** `Select` of active offices (excluding current office). `Textarea` for optional note.
- **On save:**
  1. Create `ForwardingLog`: `from_office_id`, `to_office_id`, `forwarded_by = auth()->id()`, `forwarded_at = now()`, `credit_type = null`.
  2. Update `tickets.office_id` to the destination office, `status → Forwarded`.
  3. Insert `TicketHistory` row (`event_type = Forwarded`, `note`).
- **Visibility:** Only `office_admin` and `super_admin` can forward tickets.

#### Accept Forwarded Ticket (Office B action)
- **Type:** Filament `Action` on forwarded tickets in the receiving office's queue
- **Shown when:** ticket `status = Forwarded` and the staff's office is the current `office_id`
- **Form:** `Radio` with two options:
  - `accept_credit` — "Accept Credit: counts toward both offices' performance metrics"
  - `reference_only` — "Reference Only: credit stays with the originating office"
  - Optional `Textarea` for note.
- **On save:**
  1. Find the open `ForwardingLog` for this ticket (most recent with `responded_at = null`).
  2. Set `credit_type`, `accepted_by = auth()->id()`, `responded_at = now()`.
  3. Update `tickets.status → InProgress` (or `Assigned` if assigning simultaneously).
  4. Insert `TicketHistory` row (`event_type = StatusChanged`, note includes credit decision).

#### Resolve / Close
- **Type:** Filament `Action` buttons
- **Resolve:** Sets `status = Resolved`, `resolved_at = now()`. Logs `TicketHistory` (`event_type = Resolved`).
- **Close:** Sets `status = Closed`, `closed_at = now()`. Logs `TicketHistory` (`event_type = Closed`).

### 2.3 Ticket Detail — Messaging Panel

Rendered as a Filament `RelationManager` or custom infolist section on the ticket detail page.

**Message list:** `TicketMessage` rows ordered by `created_at` ascending. Staff see all messages including internal notes. Internal notes are visually distinguished (amber background, lock icon).

**Compose area:**
- `Textarea` for message body
- **Canned Responses** button: opens a `Select` of active `CannedResponse` records scoped to the ticket's office + system-wide. Selecting one pre-fills the textarea.
- **Internal Note toggle**: when enabled, sets `is_internal_note = true` on submit. Toggle state is visually prominent (amber highlight).
- **Send** button: creates `TicketMessage` (`sender_id = auth()->id()`, `ticket_id`, `body`, `is_internal_note`, `is_canned_response = false`). If canned response was used, `is_canned_response = true`.
- **File attachment**: one file per message, max 10 MB. Creates `TicketAttachment` row.

**Seen tracking:** When staff opens the ticket detail, batch-update `seen_at = now()` for all messages sent by the requester where `seen_at = null`.

## Section 3: Forwarding Credit Logic — Full Flow

```
Office A staff/admin clicks "Forward"
  → ForwardingLog created: credit_type = null, responded_at = null
  → Ticket: office_id = Office B, status = Forwarded
  → TicketHistory: event_type = Forwarded

Office B sees ticket in list with "Pending Acceptance" badge
  → Office B admin/staff clicks "Accept Forwarded Ticket"
  → Chooses: accept_credit OR reference_only
  → ForwardingLog updated: credit_type set, accepted_by set, responded_at = now()
  → Ticket: status = InProgress
  → TicketHistory: event_type = StatusChanged, note includes credit type
```

A `ForwardingLog` with `responded_at = null` means the ticket is awaiting acceptance. The dashboard (future phase) will surface these as "Pending Acceptance" items.

## Key Design Decisions

- **No password**: All auth via Google OAuth — no email/password login routes in portal.
- **ULID as public reference**: Portal URLs use the ULID (e.g. `/portal/tickets/01JV…`), not the integer `id`.
- **wire:poll not Reverb**: Chat refreshes every 5 seconds via polling. Reverb is planned for a later phase.
- **History as audit trail**: Every state change (status, assignment, forward, resolve) inserts a `TicketHistory` row — never updates. The timeline is built from this log.
- **Forwarding credit deferred**: `credit_type = null` until Office B responds. "Pending Acceptance" is a derived state from `forwarding_logs` — no extra status enum value needed.
- **Canned responses scoped**: `CannedResponse` query returns `WHERE (office_id = ? OR office_id IS NULL)` so staff see their office's responses plus system-wide ones in one list.
- **File size limit**: 10 MB per attachment. Compression pipeline is planned for a later phase (`compressed_size_bytes` is nullable for this reason).
